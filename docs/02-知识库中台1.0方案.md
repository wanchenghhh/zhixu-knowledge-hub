# 专业知识库中台 1.0 方案（已确认）

日期：2026-10-26。状态：推荐技术组合及产品边界已由用户确认；前端原型已开发，后端待原型功能确认后推进。

## 1. 已确认的目标和约束

提供企业内部通用知识库中台，完整支持“配置模型→创建知识库→导入与构建→检索测试→在线对话→查看日志”。后台 RAG 核心链路使用 LangChain。

| 项目 | 已确认内容 |
| --- | --- |
| 使用规模 | 10–50 人，同时对话不超过约 10 人 |
| 部署路径 | 本机验证，随后企业内网 Docker 部署 |
| 登录与角色 | 首版无登录，管理员、使用者、知识库管理人员可自由切换 |
| 可见范围 | 知识库按角色限制可见；允许使用指定云端 API |
| 输入内容 | Word、PDF（文字/图片/表格）、Markdown、图片、表格 |
| 图片与表格目标 | 图片文字识别、表格内容问答，回答可追溯原文件与位置 |
| 模型服务 | 用户自行配置 OpenRouter、AIHubMix、通义；必须支持 LLM、Embedding、Rerank |
| OCR | 使用云端 API，无需下载本地识别模型 |
| 监测 | 对话查询内容、Token、使用时长 |
| 推进方式 | 方案确认→前端交互原型→用户确认→模块开发、自测和修复 |

项目起始目录无可复用代码。当前已添加 frontend 前端原型，体验与验证记录见《03-前端原型体验与验收》。

## 2. 需要明确的边界

### 2.1 角色与权限

自由切换角色意味着任何进入系统的人都能选管理员。1.0 实现角色模式下的功能与数据范围控制，不能用于区分真实员工、阻止员工主动切换角色或进行实名追责。若需要真实隔离，必须调整“无登录且角色自由切换”的前提。

采用以下已确认的角色矩阵：

| 能力 | 管理员 | 知识库管理人员 | 使用者 |
| --- | --- | --- | --- |
| 模型服务/OCR 凭证配置 | 全部 | 不可 | 不可 |
| 创建知识库 | 可 | 可 | 不可 |
| 管理文件、片段与检索参数 | 全部 | 授予管理角色可见的库 | 不可 |
| 设置知识库可见角色 | 可 | 可设置普通使用者的可见性；管理员始终可见 | 不可 |
| 在线问答、查看引用原文 | 全部 | 角色可见的库 | 角色可见的库 |
| 查询全局日志 | 可 | 不可 | 不可 |
| 查看知识库运行日志 | 全部 | 仅管理角色可见的库 | 不可 |
| 当前浏览器的对话历史 | 可 | 可 | 可 |

使用者可见的库由管理员或知识库管理人员发布。默认新建库仅管理员和知识库管理人员可见，完成构建后再开放使用者。首版只有一种“使用者”角色，不能进一步区分人事、研发或销售部门。

同一角色下的人员没有个人权限差异。对话历史用浏览器匿名会话标识区分，并按角色分区；清除浏览器存储或更换设备不保证找回。切换角色清空当前对话视图和检索缓存，再加载该角色可见会话。匿名标识不是安全身份。

后端在知识库列表、文件内容/下载、片段、检索、问答、引用和日志接口中统一校验角色范围。多库问答仅允许选择当前角色可见的库；权限撤销后，不再返回原文件、历史回答或缓存引用中的受限内容。

### 2.2 引用定位

| 格式 | 首版定位方式 |
| --- | --- |
| PDF | 原始 PDF 页码，跨页片段显示页码范围 |
| DOCX/DOC | 文件名＋章节/段落；需要固定页码时，须先生成统一 PDF 并明确是转换版页码 |
| Markdown | 文件名＋标题路径/行号 |
| XLSX/XLS/CSV | 文件名＋工作表名＋行号/单元格范围 |
| 图片 | 文件名＋识别片段；有坐标时可定位区域 |

建议首版保证 PDF 页码和其他格式的真实位置，不生成不存在的“统一页码”。保留原文件；原文查看可展示规范化正文与来源位置，原文件提供下载，PDF 提供页码跳转。

### 2.3 内容问答范围

首版表格问答针对已导入的表格内容解释与查找。不承诺跨表关联、复杂统计、公式重算或生成分析图表。图片范围为文字和表格识别，图表趋势、流程图语义理解不作为首版验收项。

建议格式清单：DOCX、DOC、PDF、MD、PNG/JPG/JPEG、XLSX/XLS/CSV。DOC/XLS 可走支持该格式的云端解析或兼容读取，必须单独验收；加密、损坏及超限文件给出明确提示。MD 内嵌远程图片默认不自动下载，提示用户单独上传。

## 3. 技术选型建议与优劣势

用户已确认采用以下各节的推荐组合；替代方案保留，供后续演进参考。

### 3.1 前端

| 方案 | 优势 | 劣势 | 建议 |
| --- | --- | --- | --- |
| React + TypeScript + Vite + Ant Design | 表格、表单、上传、步骤条等后台组件成熟；方便独立原型和内网静态部署 | 默认组件外观需要定制；开发与构建依赖 Node 工具链 | 推荐 |
| Vue 3 + TypeScript + Element Plus | 企业后台常见，表单与数据页面开发便利 | 与推荐方案相比无关键业务优势；需换用 Vue 的状态与组件体系 | 已有 Vue 团队时优先 |
| Next.js + React | 一体化路由与服务端能力，适合需要 SSR 的产品 | 本项目 Python 后端独立，内部后台对 SEO/SSR 无强需求，增加服务端职责 | 首版不优先 |

推荐前端配套 React Router、TanStack Query，图表按日志需要轻量引入。对话采用 Markdown 安全渲染及受控引用组件，避免将模型文本直接作为 HTML 执行。

参考：[Ant Design 官方介绍](https://ant.design/docs/react/introduce/)。推荐结论是结合本项目需求作出的工程判断。

### 3.2 后端与链路

| 方案 | 优势 | 劣势 | 建议 |
| --- | --- | --- | --- |
| Python FastAPI + LangChain | 可复用 Python 解析生态；异步 API、流式响应方便；RAG 与业务后端统一语言 | 需要区分异步 I/O 与 CPU 解析任务；跨进程状态必须持久化 | 推荐 |
| Python Django + LangChain | ORM、后台管理等内置能力完整 | 首版不登录且前端独立，部分能力用不上；流式接口需要额外组织 | 复杂账号与管理需求较多时考虑 |
| Node.js/NestJS + LangChain JS | 前后端语言统一，API 工程结构清晰 | 文档处理可能需要额外 Python 服务，增加跨服务边界 | 已有 Node 团队时考虑 |

推荐 SQLAlchemy + Alembic 管理业务数据与迁移，使用 SSE 从后端推送问答状态和答案。LangChain 用于加载接口、Document、分块、Embedding、Retriever、重排包装、Prompt、模型调用、流式输出与 callbacks；上传、任务状态、文件存储和权限仍由业务服务负责。

采用可控的固定 RAG 流程。首版无需为了普通知识问答加入自主 Agent、可视化工作流或远程 LangSmith 依赖。版本在真正开发时核对兼容关系并锁定，不在此处凭空指定最新版组合。

参考：[FastAPI 并发说明](https://fastapi.tiangolo.com/async/)、[LangChain 官方学习入口](https://docs.langchain.com/oss/python/learn)。

### 3.3 数据库与检索

| 方案 | 优势 | 劣势 | 建议 |
| --- | --- | --- | --- |
| PostgreSQL + pgvector | 业务、权限、日志、片段与向量集中管理，备份和一致性较容易控制 | 关键词与中文分词要自行设计；超大规模检索需专项优化 | 推荐用于首版 |
| PostgreSQL + Qdrant | 向量检索与元数据过滤专用能力丰富，可独立扩容 | 多一个服务；删除、权限更新和备份要协调两个存储 | 语料规模或检索负载明显增长时考虑 |
| PostgreSQL + Milvus | 面向更大规模向量业务，有独立扩容空间 | 对当前小团队增加部署、维护与数据一致性成本 | 首版不优先 |

推荐“向量召回＋中文关键词召回＋RRF 融合＋云端 Rerank”。关键词链路在应用层执行中文分词，再写入 PostgreSQL 文本索引；需覆盖中英混合、产品型号、文档编号和数字，不能直接以默认英文配置宣称支持中文全文检索。若所用分词库带词典，属于软件数据文件，不是本地 OCR/LLM 模型权重。

每个知识库绑定 Embedding 配置版本、维度和索引版本。初始建议使用 1024 维；其他维度需验证索引支持，再决定 vector/halfvec 或限制。切换模型即使维度相同也必须重建，不能混用不同向量空间。新索引全部成功后切换，失败保留旧版；多库查询按每库绑定模型分别构建查询向量，合并排名后重排。

参考：[pgvector 官方 README：混合检索与索引](https://github.com/pgvector/pgvector)。数据库选择是基于当前规模的建议，不能仅凭人数推导容量；最终还取决于片段数量和文件体量。

### 3.4 后台任务与原文件

| 方案 | 优势 | 劣势 | 建议 |
| --- | --- | --- | --- |
| Celery + Redis，状态存 PostgreSQL | 导入与对话进程分离；可重试、限流和多 worker 扩展 | 增加 Redis 与 worker；任务幂等和恢复需显式实现 | 推荐 |
| PostgreSQL 任务表＋独立轮询 worker | 少一个基础服务 | 租约、锁、重试和恢复调度需自行维护 | 追求最少容器时可选 |
| 仅 API 进程内后台任务 | 接入快 | 进程退出后任务恢复困难，长解析占用 API 资源 | 不作为正式版方案 |

Celery 消息不是最终业务状态。文件任务、步骤和云端 job ID 存数据库；提交采用 outbox/补偿派发，worker 按文档版本和步骤去重。云端任务恢复时先查询已有 job，避免无条件重复提交和计费；不承诺“恰好执行一次”。支持失败重试、部分失败定位和重启后的任务恢复。

首版原文件与解析产物建议存 Docker 持久卷，经后端受控访问。优点是单机部署简单；缺点是多机共享和扩容需要迁移。保留存储适配层，后续可切换企业 S3/OSS。首版无需独立对象存储服务。备份需同时覆盖数据库、文件卷及密钥配置，并验证恢复。

参考：[Celery Redis 配置与重复投递注意事项](https://docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/redis.html)。

### 3.5 文档解析与 OCR

| 方案 | 优势 | 劣势 | 建议 |
| --- | --- | --- | --- |
| 本地规则解析＋阿里云文档智能 API | 普通文本无需 OCR 费用；扫描件/图片保留结构化结果；全部推理模型在云端 | 需要维护解析路由、标准化结构及云端鉴权 | 推荐 |
| 所有文件统一云端解析 | 解析链路统一，旧 Word 等格式覆盖方便 | 上传量与调用成本更高；外部服务故障影响面大 | 文件普遍复杂时可选 |
| 通用视觉 LLM 逐页读取 | 可复用已配置的视觉模型 | 可能漏字、改写数字或遗漏表格结构；长文成本和定位稳定性需验证 | 首版不作为默认 OCR |

建议路由：MD/CSV 直接读取；DOCX 用 python-docx，XLSX 用 openpyxl，XLS 用兼容读取库；PDF 用 pypdf/pdfplumber 做文字和表格提取。扫描页、识别异常页及图片调用云端文档解析；DOC 等兼容性难点可使用云端解析。混合 PDF 按页判断，避免只检查整份文档有文字就跳过图片内容。可提取嵌入图片并识别，保留页码且去重；对复杂表格可主动指定增强解析。

云端初选阿里云 DocMind“文档智能解析”：官方说明其支持 PDF/扫描件、Word、图片，并提供版面、表格及坐标。它与百炼模型服务是不同产品，可能需要单独开通和 AccessKey，不应把百炼 API Key 当作通用凭证。优先直接上传文件流，不要求内网原文件拥有公网 URL。

“文档解析（大模型版）”覆盖格式更广，但官方能力对比说明不输出原图与坐标。两类接口不能混为一谈；首版页码定位以 PDF 原始页面映射为准。解析配置页面应允许单独配置 OCR 供应商、端点、区域与凭证。

参考：[阿里云文档理解能力对比](https://help.aliyun.com/zh/document-mind/product-overview/overview-of-document-understanding)、[格式支持说明](https://help.aliyun.com/zh/document-mind/support/faq-about-features)。

## 4. 模型配置与服务商适配

三类模型独立配置，可跨服务商组合，不能用一个全局模型覆盖全部用途。设置包含服务商、名称、模型 ID、Base URL、凭证引用、超时、并发限制、能力参数、启停与测试结果；提供默认 LLM、默认 Embedding、默认 Rerank，再由知识库按需覆盖。

| 服务商 | 对话 | Embedding | Rerank | 适配重点 |
| --- | --- | --- | --- | --- |
| OpenRouter | 支持 | 支持 | 官方已提供 RAG/重排接口说明 | 对话、向量、重排分别调用和测试，不沿用“只有聊天”的旧假设 |
| AIHubMix | 支持 | 官方说明兼容 OpenAI 嵌入接口 | 官方提供 /v1/rerank | 统一设置，按能力构建请求与解析错误 |
| 通义/百炼 | 支持 | 官方提供向量模型 | 官方提供重排模型 | LLM/Embedding 可采用兼容接口；重排依据所选 API 协议单独适配，区域与模型须匹配 |

参考：[OpenRouter RAG 与 Rerank](https://openrouter.ai/docs/guides/evaluate-and-optimize/rag)、[AIHubMix Embedding](https://docs.aihubmix.com/cn/api/EBD)、[AIHubMix Rerank](https://docs.aihubmix.com/cn/api/Rerank)、[百炼向量与重排](https://help.aliyun.com/zh/model-studio/embedding-rerank-model/)、[百炼重排 API](https://help.aliyun.com/zh/model-studio/text-rerank-api)。

模型 ID 不写死为唯一选项，用户可新增自定义模型。测试实际验证返回维度、排序索引和流式响应；凭证无对应模型权限时明确失败。具体模型可用性、额度、区域和企业网络可达性需要用户配置后实测。

凭证仅后端保存和使用，数据库密文存储，主密钥由部署环境注入；读取配置仅返回掩码和状态。浏览器不直接调用模型服务商。重排失败可按配置降级至融合结果，同时在界面与日志中标记；向量化和索引变更不静默切换模型。

## 5. 端到端流程

### 5.1 知识导入

创建知识库并绑定向量模型→批量选文件→检测格式、重复内容与限制→选择普通/增强解析→解析并保留位置→按标题/段落/表格分块→预览与调整→确认构建→向量化→建立关键词与向量索引→显示可用文件和失败项。

解析预览本身可能已调用收费 API，应在“开始解析”之前显示提示，而不是直到向量化才提示。重复文件按知识库、内容哈希、解析/分块配置版本识别；同名不同内容需要明确新增版本或替换。批次可部分成功，失败项可单独重试。

表格按行组切片并重复列标题，超长单元格保留上下文关联；原始行号不可丢失。文本默认按标题和段落切分，长度与重叠可配置并受模型输入上限约束。片段编辑后重新索引；删除/停用后立即停止检索，物理清理由后台完成。

### 5.2 在线问答

选择可见知识库→发送问题→检查角色和库状态→按需结合历史改写追问→向量/关键词召回→RRF 融合→Rerank→按阈值和上下文预算选片段→构建带来源编号的 Prompt→LLM 流式回答→校验来源编号→返回引用与用量→保存日志。

空召回默认明确说明依据不足，不使用隐藏的外部知识补答案。模型生成的引用只允许引用实际授权且已检索到的片段，后端不信任任意文件 ID。阈值按模型配置与样本调试，不能把不同模型分数当作相同量尺。

对话提供新建、历史、继续追问、停止生成、复制、重新生成和引用查看。停止生成后保留部分回答与取消状态，记录已知调用量；重新生成是新的尝试并单独统计，避免覆盖原用量。

### 5.3 管理与监测

管理员查看全局模型、任务和调用状况；知识库管理人员查看范围内的文件处理与问答日志；使用者查看当前匿名会话的对话。

问答日志可按时间、角色、知识库、模型和结果筛选，详情展示原始问题、检索用问题、召回片段、实际引用、输出、各阶段耗时、Token 与错误。多库问答若包含管理人员不可见的库，默认不向其开放该条完整日志，避免通过回答和原始问题绕过范围限制。

| 模型与解析服务 | 三服务商、LLM/Embedding/Rerank 分页、OCR 配置与测试 |
| 知识库配置 | 名称描述、可见角色、模型、检索参数、提示词与重建索引 |

参考布局：固定文字导航、顶部角色选择、内容区面包屑与主操作。在线对话用会话列表＋对话主体＋可收起的引用侧栏；导入用步骤条；日志用统计卡和明细表。默认参数与高级参数分层，技术术语附解释。

方案批准后的第一项开发交付是可点击前端原型，使用明确标识的模拟数据，不调用真实模型。需覆盖三角色、完整导入与问答路径，以及空态、解析失败、部分成功、模型未配置、无依据、网络错误等状态。原型经用户确认后再接真实后端。

## 7. 日志指标口径

| 指标 | 定义 |
| --- | --- |
| 问答端到端耗时 | 后端收到请求至完成、失败或取消 |
| 首段答案耗时 | 收到请求至发出首段可见回答，不把“正在检索”当作答案 |
| 阶段耗时 | 问题优化、查询向量化、召回、重排、生成分别统计 |
| Token | 每次上游调用的输入、输出及服务商返回的缓存/推理等字段，保留原始 usage |
| 用量来源 | actual、estimated、unknown 分开标记，未知不能按 0 汇总 |
| 调用费用 | 按配置的计价规则估算并标注；不能冒充上游真实账单 |
| 导入用量 | Embedding Token、OCR 页数、重试调用等单独统计 |
| 页面使用时长 | 如需统计，用前台活跃心跳近似；不等同于问答响应耗时 |

默认将“使用时长”理解为问答响应时长与处理耗时；若用户还要求人员在线时长，应另外确认。推理/缓存 Token 可能是总 Token 的子项，按上游定义去重，不能简单相加。无登录阶段统计维度为角色与匿名会话，无法统计真实员工用量。

建议日志保留 90 天并支持管理员调整；对话正文、调试片段与技术错误分别管理，日志不记录 API Key。日志保留期尚待确认。

## 8. 部署与容量假设

推荐 Docker Compose 服务：web（静态前端与反向代理）、api、worker、PostgreSQL/pgvector、Redis。数据库、Redis 不对外暴露，网页和 API 通过同一内部入口访问；原文件使用持久卷。

初始验证条件建议：不超过 1,000 份文件、约 100,000 个片段，普通文件 20 MB 以内，PDF 默认不超过 200 页。它们是待验证的起始限制，不是性能保证，也不由人数自动推导。云端接口限制可能更严格，按实际解析路径检查并提示。

试运行可从 4 核/8 GB 可用资源评估；实际内存、索引大小、吞吐和时延必须用样本测量，再决定容量。CPU 解析与模型网络请求分别限流，避免批量导入占满对话资源。无本地推理模型，不需要 GPU。

## 9. 模块验收与自测

| 阶段 | 必须完成的验证 |
| --- | --- |
| 前端原型 | 三角色导航、知识库可见性、导入至问答完整路径；主要异常状态可演示；键盘、溢出与中文长文案检查 |
| 模型配置 | 三服务商×三类模型逐项验证；错误密钥/错误模型/超时/限流；凭证不出现在浏览器响应和日志 |
| 文档导入 | 每种声明格式至少一个有效样本；扫描/混合 PDF、嵌入图片、复杂表格、重复文件、损坏文件；抽查原文与位置 |
| 构建与维护 | 重试不重复生成片段；重启恢复；替换、编辑、停用、删除、重建失败后旧索引可用 |
| 检索 | 建议建立 30–50 条已知答案问题；包含中文术语、型号、数字、表格、追问、无答案及越权请求；记录召回与引用正确率 |
| 在线对话 | 流式生成、停止、重试、历史、多库问答、来源跳转；没有引用时不伪造来源 |
| 角色范围 | API 直接访问、下载、引用、历史、缓存、跨库日志均校验范围；切换角色不能残留上一角色内容 |
| 日志 | 成功/失败/取消均可追踪；子调用与汇总用量一致；未知用量、重复尝试不被错误计为零或覆盖 |
| 部署 | 全新环境 Compose 启动、健康检查、数据持久化、备份恢复；约 10 路并发并记录真实瓶颈 |

每个模块自测后先修复问题，再交付确认。原型不代表 API 联调通过；模拟适配器测试不代表服务商实测通过。没有真实凭证时可继续开发与契约测试，但相应云端验收必须明确标为待完成。

## 10. 确认记录与剩余事项

1. 技术组合：React/Ant Design＋FastAPI/LangChain＋PostgreSQL/pgvector＋Celery/Redis＋文件持久卷，或指定替代方案。
2. 解析组合：本地规则解析＋阿里云 DocMind 云端 OCR/文档解析，或统一云端解析。
3. 产品边界：接受角色矩阵与自由切换限制；PDF 页码、其他格式章节/行号定位。
4. 仍可补充：初期文件数量和典型体量；日志保留期是否采用 90 天；“使用时长”是否包含网页活跃时长。

用户已明确确认前 3 项，当前进入前端原型阶段；第 4 项采用文中暂定值，在真实部署前核实。此确认步骤来自用户要求“推荐时说明为什么、优劣势，我选择后才开始开发”和“提交方案确认完成后才能进入代码开发”。
